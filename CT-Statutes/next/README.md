# CGS Reader — an exploratory redesign of the CT-Statutes explorer

This folder is a **parallel, exploratory implementation** of the Connecticut General
Statutes app. It reuses the exact same generated data in `../data/` and touches
nothing in the existing application. Same purpose and content — a different theory
of how the data should be presented.

## Run it

```bash
cd CT-Statutes
python -m http.server 8000
```

Open <http://localhost:8000/next/>.

## The design thesis

The current app is a **catalog**: you drill Title → Chapter → Section and read one
section per page, with history/annotations behind accordions and a search box that
asks you to pick a scope first. That works, but it treats each section as a database
record.

CGS Reader treats the statutes as a **document you read**:

### 1. Continuous chapter reading

A chapter renders as one scrollable page — the way statutes are actually consumed,
in context with the sections around them. A scroll-synced outline rail shows where
you are, and the URL silently updates to the section in view, so the address bar is
always a correct deep link to what you're reading. Long chapters render in chunks
so first paint stays fast.

### 2. Structured subsection hierarchy

The crawler stores statute text as flat paragraphs. CGS Reader parses the leading
`(a)` / `(1)` / `(A)` / `(i)` markers and rebuilds the nesting as real indentation
with bolded markers — the single biggest legibility change vs. the current app.
The parser handles CT's marker grammar, including the ambiguity of `(i)` as
"letter after (h)" vs. "roman numeral under (A)" (it tracks open lists and roman
succession), doubled letters after `(z)`, and multi-marker paragraphs like `(b) (1)`.
Anything it can't classify falls back to a flat paragraph, so it degrades safely.

### 3. One search, no scopes

A single omnibox (`/` to focus) searches everything at once and shows grouped
instant results: citation jump ("14-296aa" goes straight to the section), section
headings, titles, chapters, subject-index topics, and infraction entries with their
fine amounts. Enter gives a full results page; full-text search of all 81 titles is
an explicit progressive action with a live progress bar and streamed results —
no upfront choice between "navigation" and "full text" scopes.

### 4. Context in place, not behind navigation

- Fine amounts from the infraction schedule appear as a pill on the section header
  and expand inline (`Fines (30)`), rather than living only in a separate tab.
- History, annotations, and source credits are chips under each section.
- Inline citations in statute text, history, and annotations are auto-linked; a
  `#/s/<key>` resolver route locates any bare section key in the right title and
  chapter, which also makes the subject index's thousands of references clickable.
- **"Cited by" panel** on every section: which other sections' statute text cite
  this one (from a precomputed reverse-citation map, `incoming_refs.json`,
  generated by `build_incoming.py` — rerun it after refreshing the statute data),
  plus the subject-index topics that reference the section.

### 5. Subsection-level anchors

Every `(a)` / `(1)` / `(A)` marker is a link to its own URL
(`…/s/14-296aa/p/b.1`), so a *subdivision* — not just a section — can be
bookmarked or shared. Deep links scroll to the exact paragraph and flash-highlight
it. The `#/s/` resolver accepts full citations like `14-296aa(b)(1)` (the omnibox
does too), and subject-index references printed with subsections ("22-332(c)")
link straight to the subsection. While you read within a section the anchor is
preserved; scrolling into the next section retargets the URL to it.

### 6. Collapsible definition lists

Runs of three or more same-depth paragraphs that each define a quoted term
collapse into a one-line summary ("9 definitions — 'Mobile telephone' ·
'Using' · …"), so the operative text of definition-heavy sections is immediately
visible. Deep links into a collapsed definition expand the group automatically.

### 7. Reading typography

Statute text is set in a serif stack at a measured line length; UI chrome stays
sans-serif. Light/dark/auto theme, responsive three-pane → two-pane → drawer
layout, print styles. On phone widths the section tabs (Statutes · Index ·
Infractions · Saved) become a fixed bottom app bar, and the subject-index pages
repeat the A–Z letter grid inline since the sidebar lives in a drawer there.

## What's intentionally not here (yet)

This is a prototype for evaluating the presentation concept, so some production
features of the original app are out of scope:

- **Bulk "download all for offline" UI** — the app is installable as a PWA
  (manifest + `sw.js` ported from the original, plus an Install button in the
  header), and its service worker caches the shell and any data files you
  visit. The data cache name is shared with the original app, so statutes
  downloaded there (Settings → Download for offline use) are offline here too.
  What's missing is this app's own download-everything button.
- Text-size and density settings, email sharing, bookmark export.
- Bookmarking infraction entries (sections only).
- The original's boolean search operators (`NOT`, `OR`); the omnibox is
  all-terms-AND.

## Implementation notes

- Plain HTML/CSS/JS, zero dependencies, hash routing — same hosting story as the
  original (GitHub Pages, or packaged into the Android/iOS WebView shells).
- Title 42a (Uniform Commercial Code) is empty in the crawled snapshot
  (`title_42a.json` has no chapters), so cross-references into the UCC show a
  "not in the crawled data" notice with a link to cga.ct.gov. That's a crawler
  gap that affects the original app too.
- `titles_index.json` and `infractions.json` load at boot; the 14 MB subject index
  loads lazily in the background; `title_XX.json` files load on demand with a
  small LRU cache (12 titles) so a full-text scan doesn't hold ~160 MB of JSON in
  memory. Section locations found along the way are kept in a lightweight registry
  so previously-seen sections stay searchable.
- Bookmarks and recents are in `localStorage` under `cgsr:*` keys (separate from
  the original app's `cgs:*` keys, so the two apps don't interfere).
